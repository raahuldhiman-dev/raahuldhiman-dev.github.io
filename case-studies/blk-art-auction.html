01 — The Problem

Why Build a Bespoke Auction Platform?

Off-the-shelf auction plugins are built for commodity goods. Art auctions demand trust, scarcity mechanics, artist control, and an experience that reflects the value of original work. None of that ships out of the box.

⏳

Sniping Problem

Standard countdown timers reward last-second bids. Art auctions require anti-sniping: a bid in the final seconds must extend the clock to give everyone a fair chance.

🎨

Artist Trust

Artists won't list original work on a platform they don't trust. The system needed a formal onboarding, authentication verification, and a transparent payout schedule.

🚘

Delivery & Custody

Physical originals require insured tracked shipping. The platform needed to manage post-win logistics: payment windows, shipping triggers, and buyer communication.

04 — Stack

Technology Choices

Every choice maps to a specific platform requirement. No unnecessary complexity.

Layer Technology Why This Choice
Frontend Next.js (App Router) SSR for lot pages ensures fast Time-to-First-Byte and correct Open Graph previews for social sharing. ISR keeps archive pages fresh without full rebuilds.
Real-time WebSockets Auction bidding demands sub-second updates to every connected client. Long-polling would introduce unacceptable lag and stale bid displays.
Database PostgreSQL Bid races require ACID transactions and optimistic locking. Two concurrent bids on the same lot must resolve cleanly with no silent data loss.
Payments Stripe Checkout Handles PCI compliance, 3DS authentication, and webhook-driven post-payment logic (shipping trigger, artist payout schedule) without custom card handling.
API Node.js REST Shares the JavaScript runtime with Next.js, reducing context-switch overhead. Rate-limited bid endpoints prevent automated bid flooding.
Styling CSS Modules / Tailwind Minimal black-and-white brand aesthetic. Tight scoping prevents style bleed across the lot card, bid panel, and artist profile components.
Hosting Vercel + managed DB Zero-config Next.js deployment with edge caching for static lot pages. Managed PostgreSQL handles backups and connection pooling without ops overhead.
05 — Hard Problems

What Was Actually Difficult

Three non-trivial engineering problems that generic auction plugins don't solve.

⏳ Concurrent Bid Races

When two bidders submit simultaneously, the lower bid must lose cleanly without partial writes or stale reads. The solution uses a PostgreSQL row-level lock with an optimistic version counter on each lot. The API validates that the new bid exceeds the current high bid within a single atomic transaction before committing. Any race condition surfaces as a 409 conflict returned to the slower client, which the UI handles with a "you've been outbid" message and a fresh price fetch.

✓ Atomic TX + optimistic lock

⏰ Anti-Snipe Clock Extension

Standard countdown timers end at a fixed timestamp, which is trivially exploited. BLK's implementation stores the lot close time in the database, not the client. When a bid arrives within the configured snipe window, the server atomically extends the close timestamp, then broadcasts the new deadline to all WebSocket subscribers. The countdown on every connected screen updates simultaneously, so no bidder has an informational advantage.

✓ Server-authoritative deadline + WS broadcast

🔒 Authentication Before Listing

Allowing unverified work on the platform destroys buyer trust immediately. The artist onboarding flow gates lot creation behind a multi-step verification state machine: application submitted → documentation reviewed → certificate recorded → lot approved → auction scheduled. Each transition is an explicit admin action. No code path allows a lot to go live while in a non-approved state, enforced at the database constraint level, not just the application layer.

✓ State machine enforced at DB constraint level
06 — Design Decisions

Four Calls That Shaped the Product

The choices that determined the platform's reliability and trust profile.

01

One lot at a time

Running multiple simultaneous auctions splits bidder attention and dilutes urgency. A single-lot model concentrates demand, creates a shareable moment, and simplifies the real-time broadcast topology. Every bidder watches the same countdown.

02

Server-authoritative timestamps, always

Letting the client own the countdown opens the door to clock manipulation. All auction timing lives in PostgreSQL. The browser renders a countdown synced from the server on WebSocket connection and on each bid event. Client drift is cosmetic only.

03

Stripe over custom payment collection

Processing card data directly for high-value art purchases introduces PCI scope and chargeback risk. Stripe Checkout handles authentication, 3DS, and dispute evidence collection. The 72-hour payment window is enforced by a scheduled job that cancels unpaid wins and triggers re-listing logic via webhook.

04

Past auction prices are always public

Price transparency builds collector confidence. Every closed lot is archived with its final hammer price. Bidders can benchmark a new lot against historical sales before placing their opening bid, which increases participation and reduces post-win disputes over perceived value.
